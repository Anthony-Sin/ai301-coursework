# Rubric: is this plan ready to post and build from?

A package is a candidate plan plus a candidate plan comment, read
against the issue they belong to and the reproduction evidence the
plan builds on. Every check below judges an OUTCOME a stranger on the
thread could verify — never the write-up's shape, length, headings,
or polish. `references/evidence-guide.md` says where each named
evidence lives, in an eval bundle and live.

## Checks

| Check | Evidence | Pass condition | Weight |
|---|---|---|---|
| diagnosis-follows-evidence | The plan's stated cause (its diagnosis, summary, or framing line), read against every step of the package's repro evidence — including each control run, boundary test, and expected/actual pair — and against any cause the thread asserts. | The stated cause explains all of the observed evidence: if this cause is real, every repro step's result follows, including the controls — so removing that cause would remove the measured symptom. A cause the thread asserts also has to survive the package's own evidence; the thread's confidence is not evidence. Fails when any repro step or control contradicts the cause (evidence rules the blamed component out), when the plan adopts a thread-named cause the package's data excludes, when it dismisses a contradicting step by naming it a red herring instead of resolving it, or when the proposed change only suppresses the measured symptom (a guard, a catch-all, a retry on the observable) while the evidenced cause is named and left in place. | required |
| scope-bounded | The plan's in-scope statement, its not-in-scope or deferral lines, and its list of changes/files, read against what the issue and the repro evidence actually ask for. | The plan is one bounded change: every listed change serves the evidenced defect, and the parts of the defect the plan declines to fix are named as deferrals with reasons, not dropped silently — a smaller-than-possible scope stated honestly stays in scope. Fails when the fix comes wrapped in work the issue never asked for — a redesign, a dependency migration, a new option or settings surface, a framework swap, "while in the area" repairs — even when the core fix is right, and when the plan silently carves off part of the evidenced defect without calling it a deferral. | required |
| executable-by-stranger | The plan's approach/changes/steps and its files-or-areas lines, read as instructions for someone who has never talked to the author. | A stranger could start executing this week without asking anything: the files or areas to touch are named, one approach is chosen (alternatives may be noted, but one is picked), and the work is ordered enough that the first command or edit is obvious. Fails on decisions deferred to build time ("X or Y, whichever is easier", "not sure which layer"), on investigation presented as a plan ("look into", "profile and optimize", "poke around") with no chosen path behind it, or on a change with no files or areas named at all. | required |
| test-plan-decisive | The plan's test plan, read against the repro evidence's steps and artifacts. | The test plan names an observable outcome for the fix itself: the repro trigger re-run with its expected changed result (an output, an exit code, a timing, a rendered state), or a named new test asserting the behavior the evidence pins down — running the existing suite may accompany that but cannot be the whole plan, and unchanged controls or no-regression checks strengthen but do not substitute. Fails when nothing named observes the fix working (only "the suite stays green", "should feel fast", "nothing else breaks"), or when the only observable asserts something other than the evidenced defect. | required |
| comment-engages-thread | The candidate plan comment — and the direction the plan itself takes — read against the thread highlights: every explicit maintainer or owner signal bearing on the fix (a named culprit file or line, an endorsed or rejected approach, a posted patch or test binary with a testing request, a working-as-intended or limitation note, a prior-art PR the plan would duplicate). | When the thread carries explicit maintainer direction bearing on the fix, the package engages it: the plan follows the direction or openly argues an alternative on the evidence, and the comment shows the engagement rather than announcing a plan as if the direction were never given. When the thread carries no direction, the check passes on a comment that states this issue's own diagnosis, scope, and test in terms specific to it. Fails when the plan routes around explicit maintainer direction without acknowledging it (a docs-only workaround while a patched binary sits untested, a rewrite past an endorsed approach), when the comment would race a prior-art PR unacknowledged, or when the comment could sit under any issue — assign-me boilerplate, "same approach as above" piggybacking, or enthusiasm with no diagnosis or scope in it. | required |
| comms-meets-repo-policy | The repo-facts block's stated contribution policy — above all its AI-use rules — plus any stated template or contributor-flow asks, read against the candidate plan comment. | Every stated rule that applies to the comment is honored. These packages are treated as AI-assisted work: a policy requiring disclosure of AI assistance fails unless the comment actually discloses the tool and extent of the help; a policy requiring the contributor's own words fails only if the comment reads as generic boilerplate rather than specific first-person writing; a stated contributor-flow ask a plan comment can satisfy (a required field, a named format) must be satisfied. A policy that permits AI with no disclosure ask, or no stated policy at all, passes on that front. | required |
| unknowns-stated | The plan's risk, open-question, and check-at-build lines, read against the claims it asserts as settled. | Present when the unknowns the plan hinges on are named as unknowns — an open question flagged for review, a cost not yet measured, a check to run first — rather than asserted as fact, or when nothing load-bearing is genuinely unsettled. Fails only by asserting as verified fact something the package leaves open and building on the assertion with no check step; absence of a risks section in a plan that has nothing real to flag never fails. | preferred |

## Verdict rule

Accept if and only if every required check grades `pass`. A required
check graded `fail` or `unclear` rejects the package: a plan the
grader cannot verify from the package is a plan that is not ready to
build from. Preferred checks never change the verdict — they only
annotate an accepted package's strength or a rejected one's
salvageable parts.
